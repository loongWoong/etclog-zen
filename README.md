# ETC Log Merge

这个目录里的 `merge_vehicle_logs.py` 用来把同一辆车一次通行过程中散落在车道日志、ETC/MTC 服务日志、数据服务日志、名单服务日志里的相关记录归并成一个 Markdown 文件。

脚本的核心思路是：先用车牌找到一批种子日志，再从这些日志里提取能代表同一笔交易或同一辆车的关联键，反复扩大匹配范围，最后按时间线输出。

## 基本用法

最常用的方式是只指定日志目录，让脚本自动发现并聚合目录里的车辆事件：

```bash
python3 merge_vehicle_logs.py --auto --log-dir 20260514
```

默认会输出到 `20260514_merged/`。也可以指定输出目录：

```bash
python3 merge_vehicle_logs.py \
  --auto \
  --log-dir 20260514 \
  --discover-output-dir discovered
```

列出某辆已知车牌在日志目录里的候选事件：

```bash
python3 merge_vehicle_logs.py <车牌> --log-dir 20260514 --list-events
```

围绕某个时间点合并一辆车的日志：

```bash
python3 merge_vehicle_logs.py <车牌> \
  --log-dir 20260514 \
  --at '2026-05-14 08:00:28' \
  --window-minutes 4 \
  -o merged_SAMPLE_20260514_080028.md
```

常用参数：

- `vehicle`：车牌，例如 `<车牌>`。脚本也会把 `<车牌>_0` 作为初始 key。
- `--log-dir`：日志目录，默认 `20260514`。
- `--at`：锚点时间。建议总是提供，否则会扫描整个目录，容易把同一车多次通行合在一起。
- `--window-minutes`：锚点前后的时间窗口，默认 `5`。
- `--rounds`：关联扩展轮数，默认 `2`。
- `--auto`：自动发现并聚合日志目录里的车辆事件，不需要输入车牌。
- `--list-events`：只列出候选通行事件，不生成合并文件。
- `--discover`：不知道车牌时，自动从日志中发现候选车辆事件。
- `--discover-output-dir`：配合 `--auto` / `--discover` 使用，指定批量生成 Markdown 的输出目录。`--auto` 未指定时默认输出到 `<日志目录名>_merged/`。
- `--gap-minutes`：事件切分间隔，默认 `10`。同一车牌相邻两条种子日志的时间差超过这个值时，会被拆成两次车辆事件。
- `--min-lines`：配合 `--auto` / `--discover` 使用，只保留至少包含这么多种子行的事件，默认 `1`。
- `--limit`：配合 `--auto` / `--discover` 使用，限制输出或生成的事件数量。
- `-o/--output`：输出 Markdown 文件。

## 不知道车牌时

如果希望指定一个日志目录后自动完成每辆车的聚合，用 `--auto`：

```bash
python3 merge_vehicle_logs.py \
  --auto \
  --log-dir 20260514 \
  --gap-minutes 10 \
  --min-lines 20
```

这会扫描整个 `20260514/`，自动发现车辆事件，并把每个事件生成一个 Markdown 文件，默认输出到 `20260514_merged/`。

这里的 `--gap-minutes 10` 表示：同一车牌如果前后两段明文车牌日志间隔超过 10 分钟，就认为是两次不同通行事件，分别生成两个 md。调小会把事件切得更细，调大则更容易把同一车当天相邻多次通行合在一起。

如果只想先看发现到了哪些车辆事件，不生成文件，可以使用 `--discover`：

```bash
python3 merge_vehicle_logs.py \
  --discover \
  --log-dir 20260514 \
  --at '2026-05-14 08:10:04' \
  --window-minutes 2 \
  --gap-minutes 1 \
  --min-lines 10
```

输出会按候选事件列出车牌、起止时间、种子行数、关联车道和来源类型：

```text
1. <车牌A> | 2026-05-14 08:10:00 ~ 2026-05-14 08:10:31 | lines=253 | lanes=3701643301 | sources=data, etc, fee, field, mtc, namelist
```

`--auto` 也可以限制规模或指定输出目录：

```bash
python3 merge_vehicle_logs.py \
  --auto \
  --log-dir 20260514 \
  --gap-minutes 10 \
  --min-lines 50 \
  --limit 10 \
  --discover-output-dir discovered
```

这时脚本会对每个候选事件复用同一套单车归并逻辑，输出文件名形如：

```text
discovered/merged_SAMPLE_20260514_081000.md
```

批量生成时，脚本会用候选事件的时间中点作为锚点，并自动把窗口扩大到覆盖整个候选事件，避免只用事件开始时间导致后半段被截掉。

## 输出结构

生成的 Markdown 主体由脚本自动写出：

- `# Vehicle Log Merge: <车牌>`
- `log_dir`、`time_window`、`matched_lines`、`extracted_keys`
- `## Keys`：本次归并使用/扩展出的关联键
- `## Timeline`：按时间排序后的日志原文，每条带来源文件和行号

部分 `merged_*.md` 文件顶部的 `## 解读摘要` 是人工补充的解读，不属于脚本自动生成内容。

## 从 Elasticsearch 取日志

`merge_vehicle_logs_es.py` 是同一套归并逻辑的 Elasticsearch 版本：日志不再从本地 `.log` 目录读，而是从 ES 的 `message` 字段取，其余部分（明文车牌防污染、关联键多轮扩展、线圈物理事件补齐、Markdown 输出格式）直接复用 `merge_vehicle_logs.py`。因此它生成的 `merged_*.md` 照样能转成 3D 回放数据。

默认连接 `http://192.168.22.212:9200`，可用 `--es-host` 覆盖。

### 字段对应关系

实测环境为 ES 7.17，索引形如 `ump_<站点>_<yyyy.MM>`：

| ES 字段 | 含义 | 对应原脚本 |
| --- | --- | --- |
| `message` | 完整原始日志行（含 `[时间] [车道] [级别]` 前缀） | `.log` 文件里的一行 |
| `time` | 本地时间字符串，如 `2026-07-01 12:06:54.640` | 行首时间戳 |
| `@timestamp` | UTC 时间，date 类型 | 时间窗口过滤与排序 |
| `logType` | `laneLog` / `etc` / `mtc` / `data` / `fee` / `namelist` | `file_kind()` 推导出的 `sources` |
| `landId` | 车道号，如 `3701643319` | 文件名/正文里的 `37016433xx` |
| `vlp` | 车牌（`keyword` 子字段用于聚合发现） | 明文车牌 |

时间窗口用 `@timestamp` 过滤；每行的时间戳优先从 `message` 行首解析（本地时间），解析不到时依次退化为 `--time-field` 字段、`time` 字段、`@timestamp`（后两者会转成本地时区）。默认 `--time-field` 本身就是 `@timestamp`，所以实际顺序是 `message` → `@timestamp` → `time` → `@timestamp`。

### 快速开始

先看有哪些索引，以及某个时间点会自动命中哪个索引（`--index` 支持通配，并会按索引名里的月份自动裁剪）：

```bash
python merge_vehicle_logs_es.py --index 'ump_*' --at '2026-07-01 12:06:54' --list-indices
```

归并一辆车的一次通行，参数与原脚本同名：

```bash
python merge_vehicle_logs_es.py <车牌> \
  --index 'ump_37016433_2026.07' \
  --at '2026-07-01 12:06:54' \
  --window-minutes 5 \
  -o merged_<车牌>_20260701_120654.md
```

从 ES 归并必须限定时间范围（`--at` 配 `--window-minutes`，或者 `--from`/`--to`），否则会在 18M 文档的索引上全表扫描：

```bash
python merge_vehicle_logs_es.py <车牌> --index 'ump_37016433_2026.07' \
  --from '2026-07-01 12:00:00' --to '2026-07-01 12:20:00' -o merged_sample.md
```

发现候选车辆（用 `vlp.keyword` 聚合，比整窗扫描快很多）：

```bash
python merge_vehicle_logs_es.py --discover --index 'ump_37016433_2026.07' \
  --at '2026-07-01 12:06:54' --window-minutes 10 --limit 10
```

不知道车牌时批量归并：

```bash
python merge_vehicle_logs_es.py --auto --index 'ump_37016433_2026.07' \
  --at '2026-07-01 12:06:54' --window-minutes 10 \
  --min-lines 20 --limit 10 --discover-output-dir discovered
```

已知车牌时先列候选通行，再挑锚点时间：

```bash
python merge_vehicle_logs_es.py <车牌> --index 'ump_37016433_2026.07' \
  --at '2026-07-01 12:06:54' --window-minutes 20 --list-events
```

### 常用参数

- `--index`：索引模式（支持 `*` 与逗号），默认 `ump_*`；给出时间范围时会按索引名里的 `yyyy.MM` 自动裁剪到相关月份（`--no-auto-index` 关闭）。
- `--es-host` / `--es-user` / `--es-password` / `--no-verify-tls` / `--timeout`：ES 连接。
- `--time-field` / `--message-field` / `--kind-field` / `--lane-field` / `--plate-field`：字段名，换一套索引体系时改这里。
- `--log-type`：只查指定 `logType`（可重复），例如 `--log-type laneLog`。
- `--extra-query`：追加任意 ES 查询 JSON 作为 filter 片段，例如按 `sectionId` 过滤。
- `--max-docs` / `--page-size`：**单次**检索的拉取上限与分页大小，默认 `20000` / `1000`，两者都必须是 ≥ 1 的整数。触顶会告警，并在 Markdown 头部写 `es_truncated: true`；若确实存在但被 `--max-docs` 截断，头部会带上命中总数。PIT 不可用时会退化为 `from/size`，此时单次最多只能取到 10000 条。
- `--min-lines`：候选事件的最小行数（与原脚本一致）；在 `--discover`/`--auto` 下它同时作为车牌聚合的 `min_doc_count`，也就是按窗口内的文档数先过滤一道。
- `--full-window-scan`：整窗全量拉取后在本地做子串匹配，语义与原脚本完全等价（较慢，窗口大时要调大 `--max-docs`）。
- `--no-lane-scan`：关闭「已发现车道全量重扫」。
- 以及与原脚本一致的 `--at`、`--from`/`--to`、`--window-minutes`、`--rounds`、`--gap-minutes`、`--min-lines`、`--limit`、`-o`。

### 查询策略与召回

`message` 是 text 字段、按 token 检索，而原脚本是子串匹配，两者并不等价。所以 ES 侧只负责「高召回候选」，最终某一行是否纳入一律由原脚本的 `line_matches`（子串匹配 + 明文车牌防污染）决定：

1. 每个关联 key 生成 `match_phrase` 加一条前缀通配，这样 `鲁UG6595` 也能命中 token `ug6595_1` 这种带车牌颜色后缀的形态；
2. 拿到车道后，对该车道在窗口内做一次全量重扫（`landId` 字段匹配，或正文里出现该车道号），兜住 token 边界的漏召回；
3. 仍会漏的是「key 落在更长 token 内部、且不在 token 开头」的行，例如 `|流水Id:G0015370050030202091020260701120003590801` 分词后整条是 `id:g0015...`。这类行只有 `--full-window-scan` 能拿到。

实测一次 5 分钟窗口的单车归并：默认模式 277 行，`--full-window-scan` 278 行，并且默认模式**命中 key 的那些行**是严格模式结果的子集——不会多出不属于该车的行（实测多出 0 条，缺 1 条）。日常分析用默认模式，需要绝对完整时用 `--full-window-scan`。

严格来说，子集关系只对「按 key 命中的行」成立：线圈/车检器那一段是另一条按车道查询的路径，如果车道查询漏了某条落杆信号，`coil_passages` 有可能把前后两个物理过车合并成一个，选出的过车段就和严格模式不完全一致。它带来的只会是同车道、无车牌的车检器行，不会引入别的车的数据。

### 与原脚本的差异

- 去重键从 `(文件路径, 行号)` 换成 `(_index, _id)`。
- `## Timeline` 里每条来源写成 `` `logType:索引#文档id` ``，便于回 ES 复查原文。
- Markdown 头部多出 `source`、`es_host`、`index`、`es_docs_scanned`、`es_requests`（检索次数，不含 PIT/元数据请求），截断时还有 `es_truncated`。控制台那行会同时给出检索次数和 HTTP 总请求数。
- `--log-dir` 不再存在；`--at` 变成必填（或改用 `--from`/`--to`）。

## 从 ES 到可视化：完整跑一遍

```bash
# 1) 从 ES 归并一辆车，生成 merged_*.md
python merge_vehicle_logs_es.py <车牌> --index 'ump_37016433_2026.07' \
  --at '2026-07-01 12:06:54' --window-minutes 5 \
  -o merged_<车牌>_20260701_120654.md

# 2) 转成 3D 回放数据（写出 replay/data/*.json 和 replay/data/index.json）
python replay/generate_replay_data.py merged_<车牌>_20260701_120654.md --out-dir replay/data

# 3) 在仓库根目录起静态服务
python -m http.server 8765

# 4) 浏览器打开
#    http://localhost:8765/replay/index.html
#    http://localhost:8765/replay/lanes.html      （多车道过程视图）
#    http://localhost:8765/replay/vehicles.html   （车辆模型总览）
```

多车道页的数据由 `replay/generate_lane_data.py` 直接从 ES 拉取（不是从 Markdown 转）：

```bash
python replay/generate_lane_data.py --from '2026-07-01 12:05:00' --minutes 5 --out replay/data/lanes.json
```

页面左上角的下拉框会自动列出 `replay/data/index.json` 里的全部车辆事件，选中后即可播放。也可以批量生成多辆车再一起转回放数据：

```bash
python merge_vehicle_logs_es.py --auto --index 'ump_37016433_2026.07' \
  --at '2026-07-01 12:06:54' --window-minutes 10 \
  --min-lines 20 --limit 10 --discover-output-dir discovered

python replay/generate_replay_data.py discovered/merged_*.md --out-dir replay/data
```

三点注意：

- 必须从仓库根目录启动 `python -m http.server`，因为页面用相对路径 `./data/index.json` 取数据。
- 必须通过 `http://` 访问。直接用 `file://` 打开 `replay/index.html` 会因为浏览器的 ES module/跨域限制而加载不了 three.js。
- 如果不用 8765 端口，换成 `python -m http.server 9000`，URL 里的端口同步改掉即可。页面左上角下拉框为空，通常是因为第 2 步没跑或 `replay/data/index.json` 不存在。

## 3D 回放

`replay/` 目录里有一个基于 Three.js 的静态回放器，可以把 `merged_*.md` 转成车辆过站/出站的语义回放。

如果本地还没有 `merged_*.md`，先用单车或自动聚合命令生成 Markdown。生成后的 `merged_*.md` 属于本地分析产物，默认不会提交到 Git。

先把 Markdown 转成回放数据：

```bash
python3 replay/generate_replay_data.py merged_*.md --out-dir replay/data
```

再在仓库根目录启动静态服务：

```bash
python3 -m http.server 8765
```

浏览器打开：

```text
http://localhost:8765/replay/index.html
```

也可以直接打开某个回放文件：

```text
http://localhost:8765/replay/index.html?file=merged_SAMPLE_20260514_080028.json
```

页面操作：

- 左上角下拉框选择车辆事件。
- 底部 `播放/暂停` 控制回放，进度条可以拖到任意日志事件。
- 倍速支持 `0.05x`、`0.1x`、`0.25x`、`0.5x`、`1x`、`2x`、`4x`。
- 右上角两个视角按钮：`全景`、`车道现场`，点击后相机平滑切到对应视角。
- 鼠标左键拖拽旋转视角，滚轮缩放，右键拖拽平移视角。
- 右侧面板只显示本次通行标题和日志列表；当前事件会高亮，并跟随播放自动滚动。
- 点击右侧任意日志行，可以跳到对应事件并暂停播放。
- 右上方有车辆信息卡片：号牌（按日志车牌颜色着色）、车型（部车型码与来源）、轴数、长×宽×高、车身颜色（含来源标注）、质量；车身颜色下拉框可以手动指定，改完立即重建车辆模型。

场景只保留车道现场：

- **车道现场（通行设备）**：沿车辆行驶方向（+Z）按实际过车顺序排布：`车牌识别 → 称重/治超 → 车型识别 → 车检器1 → 前 ETC 天线（预交易）→ 车检器2 → CPC 读卡 → 车道控制器 → 车检器6（存在线圈）→ 后 ETC 天线（交易）→ 费显/LED → 车检器7（落杆线圈）→ 栏杆`。线圈和称重平台在路面上，栏杆、费显、CPC 读卡、车道控制器放在右侧收费岛上，车牌识别/车型识别/车道摄像机用立柱横臂悬在车道上，前后 RSU 由龙门架承载，岗亭、关道设备、存在线圈标注等按车道类型显示。
- **收费系统服务不建模**：交易服务、名单服务、计费服务、消息/MQ、流水/Redis 这些后台服务不占车道上的位置，画面里不再有「虚拟机房」「虚拟省中心」及其链路，也不再建机柜、空调、配电柜、核心交换等配套。它们的日志照旧出现在右侧时间线里，但点击这类事件时相机不动、也不高亮任何模型（现场没有对应实体）。

车辆模型上带有 OBU 车载单元；当日志事件属于 RSU/OBU 通信时，会高亮 RSU 到车辆 OBU 的通信连线；`success` 事件会把栏杆臂抬起（绕岛上的转轴旋转），`reject` 事件落杆。右侧时间线同步显示对应日志原文。

车辆本身按日志时间单向沿车道推进；当前事件对应的设备节点会高亮。这样可以避免后台补写流水、牌识匹配、MQ 回执等事件把车辆“拉回”到前面的设备位置。左侧图例只有「通行设备 · 车道现场」一组；被车道类型过滤掉的设备（例如 ETC 车道里的称重/治超、CPC 读卡）平时不显示，但当事件正好落在它身上时会临时显示，避免高亮一个看不见的对象。

车辆本身按日志时间单向沿车道推进；当前事件对应的设备或服务节点会高亮。这样可以避免后台补写流水、牌识匹配、MQ 回执等事件把车辆“拉回”到前面的设备位置。

线圈会按车道类型显示为具体车检器位置。ETC 车道中，`车检器1` 对应从左往右第一个车辆检测器，`车检器2` 对应第二个车辆检测器，`车检器7` 对应落杆线圈；MTC/混合车道中，`车检器6` 对应存在线圈，`车检器7` 对应落杆线圈。如果日志中出现 `车检器x` 或 `线圈为:x号`，回放会高亮对应线圈。

### 车辆车型与颜色：日志里有什么、没有什么

回放里的车辆外观分三层证据，逐层降级，页面上会标出每一条的来源：

1. **车型（可靠）**：`车型码` 是部标 JT/T 489 的车型分类，日志里有两路来源——ETC 卡/OBU 申报（`车型码`、`卡内货车轴数`）和车型识别设备实测（`identifyType`、`vehicleAxleCount`、`vehicleLength/Width/Heigth/WheelBase`，尺寸是十六进制毫米，如 `2EDE`=11998mm）。两者不一致时两条都保留并标注（例如申报货三、识别货六、实测 6 轴）。实测尺寸只在「与车型族相符」时才采用，否则退回车型典型值，避免把邻车尺寸套上来画出 22 米的轿车。
2. **车牌颜色（可靠，但码表要自己验）**：`licenseColor` 没有随日志给出码表。用 2026-07-01 11:00–13:00 的 6000 条样本做车型×车牌颜色交叉验证，得到 `0 蓝 / 1 黄 / 2 黑 / 3 白 / 4 绿 / 255 未上报`：黄牌只出现在货车（车型 12/13/14/16）上，蓝牌只出现在客车（车型 1–4）与轻货上，与常识一致；若按「1=蓝」的另一张表读，重卡会变成蓝牌，自相矛盾。车牌颜色用于渲染号牌底色。
3. **车身颜色（不可靠）**：牌识 `VehPlateReport.vehicleColor` 有 81% 上报 `0`/`00`（未知），其余取值分散，日志里没有码表；车型识别设备的 `vehicleColor` 恒为 `00`。所以**不能**从日志断言车身颜色：页面默认标注「牌识车身色码 N（厂商码表未验证）」，无码时按车型常见配色示意，并提供下拉框手动指定。另外 `vehicleModel` 字段在 749 条样本里恒为 `0000`，完全没用。

车型码 → 模型映射：`1` 轿车 / `2` 中客 / `3` 客车 / `4` 大客 / `11` 轻卡 / `12` 两轴货 / `13` 三轴货 / `14` 四轴货 / `15` 半挂五轴 / `16` 半挂六轴 / `21`–`26` 专项作业车。

### 拟真车辆模型（`replay/vehicle-models.js`）

`buildVehicleModel(spec)` 按上面的车型属性生成整车：

- 轿车/客车：侧面轮廓 `ExtrudeGeometry` 拉伸（车顶、玻璃带、前后灯、后视镜）；
- 货车：驾驶室 + 货箱（瓦楞板、后门、侧防护栏、反光条、挡泥板）；
- 半挂：牵引车 + 挂车（鞍座、支腿、后防撞、挂车轴组），轴位按牵引车/挂车各自长度计算；
- 专项作业车加警灯与作业支腿，危险品车加菱形告示牌与橙色标牌。

轴数按日志（2–6 轴，重货后轴双胎）；尺寸优先用日志实测值（与车型族相符时），否则用车型典型值；号牌用 `CanvasTexture` 画真实车牌底色（蓝/黄/绿/白）。车身颜色未知时按车型给一组确定性配色，保证同一条日志每次回放颜色一致。

约定：`+Z` 为行驶方向、`+X` 为车辆右侧、车轮落在 `y=0`、原点在车辆中心。多车道页里每趟过程会按该趟车的车型重新建模，过程结果用车辆上方的悬浮标记表达（放行绿/拦截红/混合橙/未知灰），不再把结果色刷在车身上。

想单独看模型，可以打开车辆模型总览页（11 个车型族摆成一张展台，鼠标可旋转，默认缓慢自转）：

### 场景观感（`replay/scene-look.js`）

三个页面共用同一套光照与材质，避免同一场景在不同页面里亮度、阴影各不一样：

| 项目 | 做法 |
| --- | --- |
| 天空 | 程序化等距柱状贴图：天顶到地平线的渐变 + 太阳方位的日晕/日面 + 积云/丝缕（云在**天球**上布点，再按等距柱状投影画成椭圆，向阳面亮、背阳面偏冷灰，见下），做成**挂在相机上的穹顶网格**（不是 `scene.background`，原因见下） |
| 环境反射 | 天空贴图经 `PMREMGenerator` 变成环境贴图 → 车漆/玻璃/金属有真实反光，而不是靠高光「假装」 |
| 阳光与阴影 | `DirectionalLight`（正午高度角 58°）投射到整片广场，`PCFSoftShadowMap` 2048² + 法线偏移；半球光补天光与地面反弹 |
| 影调 | 整帧统一 `ACESFilmicToneMapping` + `SRGBColorSpace`（走渲染管线，见「泛光」一行），避免高光一片死白 |
| 泛光 | `EffectComposer` + `UnrealBloomPass`：太阳、警示灯、刹车灯、设备状态灯在远景也发光；软件渲染下不建泛光 pass，但同样走 `RenderPass + OutputPass` |
| 路面 | 程序化沥青/混凝土颗粒贴图（按米重复）+ 轻微凹凸，配雾与远景大地面，让地平线不是「世界边缘」 |
| 阴影角色 | 建完场景后按包围盒自动分配：大块地面只接收，设备与车辆投射+接收 |
| 车轮 | 每根轴一个轴组（原点在轮心线上），按行驶距离 `Δz / 轮半径` 滚动 |
| 刹车灯 | 每辆车一套自己的尾灯材质 + 尾部两个加法混合光晕；按实际位移算速度和减速度，减速即亮、停住后再亮 2.5 秒后熄灭（松开刹车） |
| 接地阴影 | 车下一片径向暗斑（AO）。软件渲染时太阳阴影会关掉，这一片保证车"踩在地上"而不是悬空 |

天空为什么不用 `scene.background`：three 对 sRGB 背景贴图**不施加色调映射**（当作显示参考色直接输出），
而渲染进 render target 的泛光管线里 `OutputPass` 会对整帧统一施加 ACES —— 同一页面在"直接渲染"和"管线"
下会出现两个不同的天空（实测画面差异 1.2/255、最高 200/765，过曝像素 2.96%）。改成普通穹顶网格
（`toneMapped` 走默认值）后两条路径逐像素一致，差异降到 0.19/255、过曝像素 0.02%。

泛光与统一色调映射：`RenderPass →（有 GPU 时）UnrealBloomPass → OutputPass`，渲到 half-float 线性
`WebGLRenderTarget`（GPU 上开 4x MSAA）。**没有 GPU 时不建泛光 pass，但同样走这条管线**：three 在没有
render target 时按 `outputColorSpace` 处理雾色/背景这些"不受光 uniform"，渲到 RT 时按线性工作空间处理
（`getUnlitUniformColorSpace`），两条路径的雾与天空会不一样 —— 统一走管线后实测"软件路径 vs 有 GPU 关
泛光"**逐像素一致**（meanDelta 0、changedRatio 0）。代价是软件路径每帧多 1 次全屏 pass（draw call
178 → 179，index 页），泛光开启时再多十几次（高光提取 + 5 级 mip 双向模糊 + 合成，178 → 192）。
泛光参数（0.18 / 0.45 / 1.4）与三个页面的实测表见 `replay/LANES_README.md` §6.4。

软件渲染（SwiftShader / llvmpipe 等）时自动关掉阴影贴图、压到像素比 1、天空贴图降到 768²、不建泛光 pass：阴影与五级模糊都是每帧额外的渲染通道，在没有 GPU 的机器上会把 CPU 打满（见 `render-runtime.js` 的 GPU 优先策略）。

### 天上的云：按天球投影，而不是在画布上画圆（`replay/scene-look.js`）

天空是等距柱状（equirect）贴图，**行**是极角、**列**是方位角。所以同样一个"视角半径 ρ 的圆"，
投到画布上必须是椭圆：竖直半轴 `Δθ = ρ`，水平半轴 `Δφ = ρ / sin(高度角)`。
原来那版直接在画布上 `arc()` 画圆，等于把天顶的云压窄、地平线的云拉宽 —— 一眼就假。

`skyCloudLayout()` 是纯函数（不碰 canvas），`paintSkyClouds()` 只负责画，于是云**投回天球上是不是圆的**
可以用恒等式在 Node 里钉死（`python _smoketool.py _smoke/sky-check.mjs && node _smoke/sky-check.mjs`，16 项全通过）：

| 做法 | 为什么 | Node 侧实测 |
| --- | --- | --- |
| 在天球上撒点：`sin高度角` 在 [0,1] 上**均匀** | `dA ∝ d(cosθ)`，均匀取 y 才是天球上面积均匀，否则云全挤在天顶 | 均值 0.530、十段分布 1/10/7/4/5/6/9/8/7/5（无空段） |
| 视角半径 ∝ `sin高度角` | 云在一个水平云层上，仰角越低距离越远（`d = H/sin高度角`），同样的云看着越小 | 基准角 4.8°~16.0°；低 14 团均 2.0° vs 高 16 团均 8.0° |
| 每团写成 3~6 个"泡" + 一圈淡云缘 | 圆形的云就是假的；泡挤在一起才有轮廓，软边才不生硬 | 每团实际 1074 笔弧（62 团） |
| 亮度按 `cos(与太阳夹角)`：向阳接近纯白、背阳偏冷灰 | 云的白是太阳打的，不是自发光；背光面真实照片里就是灰蓝的 | 向阳 252 vs 背阳 148（RGB 全部 ≥148，不会黑到脏） |
| **先画太阳、再画云** | 原来云画在太阳之前，云永远盖不住日面/日晕 —— 物理上错的 | 贴图带回 `userData.skyClouds`（云量、挡日系数），供自检核对 |
| 画云前先 `clip` 到地平线以上 | 旧代码云团中心最高到 `0.40H`、半径最大 190×2.1=399px，云缘会落到 `0.79H`（地平线是 `0.5H`）—— 云漏到地面雾里 | 断言"先裁再画"：`rect` 1 次、且画第一笔弧时 clip 已生效 |

画出来的那一份由浏览器自检核对（`report_sky`）。有两点是这一轮才搞清楚的：

* **默认机位根本看不到天**：lanes 默认是 58m 高俯视（45° 视场只覆盖水平线以下 14.9°~59.9°）、展台是近景转台，
  天空像素都是 0；index 也只有 0.4%。所以天空的数都在一个**抬高机位**（55°）上量，并且要把穹顶
  `position.copy(camera.position)` 挪过去 —— 天穹是按 `followSky(camera)` 挂在相机上的，不挪的话机位在球壳外面，天会凭空消失。
* **云的净贡献用"换掉云层"直接量**：`skyCanvasTexture({clouds:false})` 生成同一套天空的无云版本换上去前后差一帧。
  之前想用"又亮又几乎不偏色"当云量代理指标，实测它量到的主要是地平线那层灰白雾，跟"有没有画云"几乎无关。

| 量什么 | index | lanes | vehicles |
| --- | --- | --- | --- |
| 抬高 55° 机位里天空占画面 | 100.0% | 100.0% | 100.0% |
| 换掉云层后的变化像素（55° 机位） | 42.2% | 30.9% | 36.4% |
| 其中提亮（均 +60/255）、最大逐像素差 | 5.5% | 2.5% | 4.1%（最大 312~314） |
| 同样这批云在抬 17° 那条机位只改变 | 2.4% | 1.7% | 2.7% |
| 天空相邻像素梯度（抬 55°） | 0.25 | 0.27 | 0.19 |
| 天球云量 / 积云 / 丝缕 | 34.7% / 62 团 / 9 条（三页同一张贴图） | | |

17° 那条几乎没云不是 bug，正是"云层是平的"的结果：地面被透视压掉，低仰角那一条本来就空，云都堆在头顶
（`sin²ε/cosε` 在仰角高处发散的同一件事）。同一天空在抬高机位的变化是低仰角的 **15~18 倍**。

天空贴图同时喂给 PMREM 环境反射，所以云也会出现在车漆里。**半球平均亮度**是照明的输入，
这一轮从 `[0.169, 0.320, 0.570]` 变成 `[0.178, 0.326, 0.569]`（线性），B/R 3.37 → 3.2：
影子颜色与假影贴图都是从这个值算出来的，所以它们跟着一起变，不需要另改。

旧自检里"天顶那一格必须是蓝的"这条改掉了：有云的时候天顶那一格本来就可能是白云，**一格发白不等于整片天糊了**。
现在用半球平均判蓝不蓝（B/R ≥ 1.5），再用逐带"没有任何一带过曝（≥251）、地面带够暗（≤120）"守住"白幕"这个坑。

云的**数量**是选出来的，不是从日志推出来的（日志里没有天气）：34.7% 的天球覆盖率 ≈ 少云到多云，
三页共用一张贴图（同一天、同一颗太阳、只有 2.7 分钟数据，见「影子为什么是蓝的」一节）。

### 场景道具与地面细节（`replay/scenery.js`）

让收费站不再"只有设备浮在一块板上"（同一份代码给 index 与 lanes 两个页面用，所以两页场地观感一致）：

| 道具 | 做法 |
| --- | --- |
| 波形梁护栏 | 沿广场两侧长边（进出车道方向留空），立柱用 `InstancedMesh`（几十根柱只画一次）、双横梁，立柱埋地 5cm |
| 路灯 | 沿两侧护栏内侧每 26 米一根，灯杆/底座/灯臂/灯头/灯罩分件，灯臂朝场地内 |
| 行道树 | 护栏外两排交错 + 远端一排挡地平线；树干与树冠各一个 `InstancedMesh`（99 棵 ≈ 2.4 万三角形），树冠由 3 个球叠成，大小/朝向/色相用确定性随机 |
| 岛头警示条纹 | 收费岛两端的黄黑斜纹（`CanvasTexture`），ETC 收费岛最典型的一眼特征 |
| 车道标线 | 两侧白色实线 + 栏杆前 3 米的停止线（与 6 米一道的车位标线不重叠） |
| 轮胎磨损痕 | 车道内 ±0.62 米两条半透明深色带（真实车辙位置） |

### 地表风化与远景层次（`replay/weathering.js`）

真实收费广场不是一块刚铺好、擦干净的新沥青，地平线后面也不会只有一条雾线。这一层专门补这两件事：

| 项目 | 做法 |
| --- | --- |
| 大尺度脏污/水渍 | 一整片盖住广场的**乘法**贴片（白=不变、越暗越脏）：修补色差、油渍、水渍、细裂缝。乘法叠加只压暗不提亮，不会破坏已定好的明暗关系 |
| 沥青补丁 | 6 块（多车道页 10 块）方正深色修补面，边缘干脆、比原地更粗糙 |
| 裂缝 | 8 条折线（多车道页 12 条）细长深色线，宽 4~9cm |
| 排水沟与篦子 | 贴着收费岛底一条长沟 + 4 只铸铁篦子（多车道页每条车道各一条，长度对齐岛体 54m） |
| 井盖 | 铸铁盖 + 略大的井座，成对出现 |
| 地面粗糙度图 | 程序化**数据贴图**（非颜色）：轮迹被磨光、低洼积水更光滑，环境反射因此有层次；只影响反射那一项 |
| 远景层次 | 5 座远山剪影（不受光，靠雾融进天空）+ 5 座厂房与屋面 + 2 只筒仓 + 一道远处树墙，全部被雾一化，给地平线分出前后层次 |

"藏起来看画面变没变"的因果检验（无头 `gl.readPixels` 回读）：地面风化影响 index 页 **51.8%** 的像素
（平均差 6.76/255）、多车道页 **54.3%**（6.85/255），且变化集中在画面下半部（下 79%/69%）；远景层次影响
index 页 **10.7%**（平均 5.01/255），且只出现在画面上部两行 —— 就是地平线那一带。

相机远平面也为此从 400 提到 600（index）：远景放在 z≈-205、最远 265m，而最远机位在 190m 处，
400 会把远山整块裁掉；深度精度主要由 `near` 决定，改 `far` 几乎不影响近处贴片（贴片另有
`polygonOffset` 兜底）。多车道页默认是 58m 高的俯视机位，视场只覆盖水平线以下 14.9°~59.9°，
**地平线根本不在画面里**（远景层在那里贡献 0 像素），把相机压低/拉远才看得到 —— 自检里用一个
探针机位专门验证了这一点。

### 接地暗部（`replay/contact-ao.js`）

没有 GPU 的机器上太阳阴影是整块关掉的（每帧一次阴影通道会把 CPU 打满），于是设备、路灯、树、
护栏立柱全都像"贴"在地面上。这一层自动把场地里**所有立在地上的构件**扫一遍，给每个构件铺一片
贴地暗斑，而且不是随便一片圆：

| 规则 | 做法 |
| --- | --- |
| 选谁 | 立着（自身高度 ≥0.2m、顶面高过地面 0.5m）、底面最短边 ≥12cm、不是"又长又矮"的横梁，且底边确实落到支撑面上 |
| 不选谁 | 车辆（有自己的接地阴影）、地面标线/箭头/线圈、风化贴片、天空穹顶、150m 外的远景层 |
| 多大 | 真落地的按底面给（半径≈半个占地跨度+0.4m）；被支撑在空中的（低垂树冠）尺寸封顶 2.2m，免得一排树连成暗沟 |
| 朝哪 | 沿**太阳影子方向**拉长并偏移：影长 = 高度 × cot(高度角)，正午 58° 就是 ≈0.62 × 高度；矮东西几乎只有接触暗部，高杆拖出一条软影 |
| 怎么画 | **乘法**混合（白=不变、暗=压暗，地面颗粒能透出来），全部实例合成**一个 InstancedMesh**：只多 1 个 draw call |
| 什么时候 | 最后一步执行，放在 `applyShadowFlags` 与风化/远景之后；多车道页关掉「细节」时会重建（岗亭/设备一消失，暗斑跟着消失） |

index 页 82 片（树 55 / 设备 16 / 路灯 8 / 门架腿 3），lanes 页 263 片（8 条车道每条约 30 片）。
多车道页关掉「细节」时暗部会跟着重建（263 → 226 → 263，差额正好是挂在细节组里的岗亭与设备），
不会留下一地幽灵暗斑。"藏起来看画面变"：index **0.88%** 像素、lanes **2.73%** 像素，方向
**全是被压暗**（0 个变亮），画面最上两行（天空/地平线）一点不动。自检还会逐实例核对假影的朝向、
长度、偏移是不是按 `cot(58°)=0.625` 算出来的，并确认没有一片落到 150m 外的远景层上。

这一层只是**接触暗部**（贴根、软的，拉长上限压在 3.2 倍）；灯杆/雨棚/树冠那条真正的**硬影**
在 `prop-shadows.js`（见下），两层共用同一个太阳与同一个影色乘数。

### 道闸动作（`replay/barrier-arm.js`）

收费广场最有标志性的一段动作是抬杆/落杆，之前两页都只把臂挑起来 26°（几乎是水平的），
姿势还是"每帧朝目标缓动"攒出来的 —— 拖时间轴跳着看，同一时刻能看出两个不同姿态。

| 项 | 现在的做法 | 依据 |
| --- | --- | --- |
| 抬起角度 | **−86°**（臂接近竖直，端头从 1.12m 抬到 **7.16m**） | 直臂道闸实际抬到 80~90°，不是 26° |
| 行程时长 | 抬 **0.9s** / 落 **1.1s**，缓入缓出 | 落杆比抬杆慢是设备的安全设定；日志里"控制指令→到位上报"只有几十毫秒，是握手时间，**量不出机械行程**，所以时长是视觉约定 |
| 状态来源 | 日志的**抬杆到位 / 落杆到位**（含控制指令里的 `00-落杆`/`01-抬杆`） | 不是按通行结果猜的；日志里没有栏杆事件时才退回按过程结果推断 |
| 角度公式 | **跳变序列 + 时刻**的纯函数，中途反转从当时的实际角度接着走 | 拖到哪一秒都是同一个角度，可复现、可核对 |
| 外观 | 红白相间直臂（12 段，段间暗缝）+ 白端头 + 转轴配重 | 中国收费站直臂道闸的常见涂装 |
| 杆座警示灯 | 运行中 **2Hz 黄闪**，到位即灭；相位也由时刻决定 | 真机运行时会闪；相位确定才能自检 |
| 两页一致 | 单车道页与多车道页共用同一个建模/公式模块，只有驱动方式不同（事件步进 vs 时间游标） | 免得两页的栏杆长得不一样 |

实测（lanes 页，同一机位把臂藏起来再画一帧，差异像素就是臂本身）：

| 状态 | 屏幕上的形状 | 长宽比 | 红/白像素 | 红白相间次数 |
| --- | --- | --- | --- | --- |
| 落杆到位 | 246 × 16 px 横条 | 15.4 | 474 / 536 | 12 |
| 抬杆到位 | 24 × 217 px 竖条 | 0.11 | —— | 4 |

行程采样：抬杆后 0.15s / 0.45s / 0.75s 分别 −4.8° / −43.0° / −81.2°，对应端头 1.62 / 5.25 / 7.10m；
同一时刻拖回来两次读数**完全一致**（旧的按帧缓动做不到这一点）。index 页则验证"触发瞬间还在地上
（0°、标记为行程中）→ 行程走完后 −86°、端头 7.16m；落杆回到 0°、端头 1.12m"，
并确认行程中警示灯亮过、到位后熄灭。

### 车辆接地阴影：跟太阳走（`replay/vehicle-models.js`）

车辆脚下原本是一片**对称的径向暗斑**——贴地一圈，和太阳没有任何关系。同一画面里，接地暗部
（`contact-ao.js`）已经按 `cot(58°)=0.625` 铺出了带方向的影子，两边各说各话，看起来就像有两个光源。

现在两层共用同一个取法：`scene-look.js` 导出 `sunShadowFrame(direction)`，一次给出地面影子方向
（x/z）、影长系数 `cot` 和方位角；`contact-ao.js` 与 `vehicle-models.js` 都从这里取，不再各算一套。

| 项 | 做法 |
| --- | --- |
| 影长 | 车顶在地面上的位移 `sweep = cot(高度角) × 车高`，正午 58° 就是 ≈0.625 × 车高 |
| 片形 | **真扫掠形状**：车身占地矩形沿影子方向平移 `sweep` 后的凸包（"矩形 + 扫出去的那条"），逐几何算出来画进贴图 |
| 位置 | 整片沿影子方向平移 `sweep/2`：近端贴在车身背光边，远端正好落在车顶影子的尖上 |
| 影色/深浅 | **不再手调深灰**：`天光 / (天光 + 直射太阳)` 逐通道算出来（见下），写进贴图画布 |
| 混合 | **乘法混合**（与接地暗部同一套）：白=完全不变、色调=影子里的乘数；`toneMapped:false`、`fog:false`、底色纯白 |
| 明暗 | 扫掠形状内**整片同一个乘数**（影核），没有"从车底往影尖越来越淡"——那是美术处理不是投影 |
| 半影 | 边界只留一圈物理半影：`2 × 太阳视半径(0.266°) × 车高/sin高度角` + 0.04m 软边。4.05m 半挂 ≈0.084m、1.5m 轿车 ≈0.056m |
| 朝向 | 每一帧按**太阳**摆，不按车头：局部转角 = 影子方位角 − 车体世界朝向 |

### 影子为什么是蓝的、为什么这么深：从场景自己的灯算（`scene-look.js`）

太阳被车身挡住之后，影子里的地面**只剩下天光**。所以影子的颜色不是拍出来的深灰，而是天光的颜色
（偏蓝），深度就是"直射占了多少"。`groundShadowRatio()` 就用场景里那几盏灯算：

```
直射 = 太阳色 × 强度 × sin(高度角)          = (2.714, 2.547, 2.105)
天光 = 半球光 + π × 天空平均亮度 × 路面envMapIntensity(0.35) = (0.547, 0.868, 1.303)
影色 = 天光 / (天光 + 直射)                = (0.168, 0.254, 0.382)   ← 蓝是红的 2.27 倍
```

三处细节是这一轮踩出来的，缺一个数字就不对：

| 细节 | 为什么 |
| --- | --- |
| 天空平均亮度**要扣掉日面/日晕**（30° 锥，占天光 17.6%） | 日晕是**直射**被前向散射的那一份，已经在直射项里算过；再算进环境漫射就是双份，影子会虚亮近一倍 |
| 穹顶贴图与 PMREM **必须按同一套 equirect 采样** | `SphereGeometry` 自带 UV 的 u 与 equirect 差一次 z 的镜像（球面 u=0.25 在 +Z，equirect 在 −Z），同一张天空贴图当背景和当环境贴图时太阳落在两个地方 |
| 日面位置按 `atan2(cos方位角, sin方位角)/2π+0.5` 画 | 原来直接拿 `方位角/360` 当列号，与本工程"0° → +Z"的约定差一次镜面，**天上那颗太阳离灯 90°**（影子朝一边、太阳在另一边） |

另外天空画布本身也修了一处：云用 `lighter`（加法）叠 ~100 个软团会把整片天推到纯白
（实测 768 宽的画布上半球全是 `255,255,255`），天空成了白幕、环境漫反射也成了白的，影子算出来发灰。
改成 `source-over`（天然有界）并把云团半径按画布宽度缩放（原来半径是绝对像素，低配天空下云糊满全幅）。

| 项 | 读数 |
| --- | --- |
| 天空画布分带 | 天顶 `[69,125,204]`（蓝）、中天 `[162,202,245]`、地平线 `[174,184,193]`、地面半天 `[48,55,63]`——**没有一格过曝** |
| 日面位置 | 128×64 细网格里最亮的一格 uv `[0.41, 0.164]`，与灯光方向夹角 **3.3°**（>12° 就说明天上那颗太阳与影子朝向不是同一颗） |
| 影色 = 场景灯光 | 贴图里的乘数 `[0.168, 0.254, 0.382]` 与探针**独立复算**的 `天光/(天光+直射)` 逐通道最大差 **0.0** |
| 影核均匀性 | 影核 9 点取样，逐通道极差 ≤0.02；格点里最弱覆盖度 **0.999**（1 = 全影） |
| 落地效果（正上方同批像素） | 影子里 `[0.171,0.228,0.307]` vs 太阳下 `[0.341,0.39,0.451]`：亮度比 **0.577**，蓝红比 **1.791 vs 1.325** |

旧写法是"旋转矩形"——矩形沿影子方向平移后的**包围盒**，长车在近垂直日照下会多铺出两个角。
现在的贴图是真扫掠：在车身坐标系里取 4 个占地角点，各加一份沿影子方向平移 `sweep` 的副本，
8 点取凸包，再把这 8 个点映射进画布。

| 项 | 读数 |
| --- | --- |
| 多铺多少（整块矩形 ÷ 真扫掠） | 11 辆里 **1.24 ~ 1.51 倍**；最大那辆 2.5×18.5m 车高 4.05m：真 **93.49m²** / 矩形 **140.98m²** |
| 贴图覆盖核对 | 平面里铺 17×17 格，逐格比"贴图这一格反推出来的覆盖度"与"解析上在不在扫掠里"：**越界被压暗 0 格 / 该暗没暗 0 格**（半影带与 2 个 texel 以内不判：画布只有 256×96，一格就是十几厘米） |
| 平面横向 | `crossPlane = cross + 2×半影`，与 `scale.x` 一致 |

这一轮真正的问题几乎都是自检的像素量抓出来的，记在这里免得以后重犯：

| 症状（自检读数） | 原因 | 修法 |
| --- | --- | --- |
| 展台上影子跟着车头一起转 | 影子挂在车体下，转台一转世界朝向就变了 | `onBeforeRender` 里按车体世界朝向反向补转角，并顺手刷新矩阵（否则慢一帧）；局部角误差 ≤0.006° |
| 正上方机位重心方向差 ~107° | 平移量直接写了**世界**方向，落到局部坐标里就偏了 | 平移用局部影子方向；另加一项核对"平移量的世界方向 = 影子方向" |
| 半挂的影子整片铺到车厢外面 | 基准点了车体**组原点**，而半挂车体长在 +Z 一侧 | 基准改用车体实际占地中心：实测组的原点和占地中心差了 **5.29m** |
| 影子看起来落在**向阳**一侧 | 贴图"只压车底、往外迅速淡掉"；车底那片被车身挡住，肉眼看到的主要是露在车外的一圈 | 改成"车底到背光边接近满强度、最后一段淡出" |
| 形状核对"越界被压暗 4 格" | 贴图按整数度缓存、转台一直在转，**图里那一版形状**与当前帧的方案差半度 | 贴图自己记一份 `userData.shape`，核对用"图自己的几何"（刻舟求剑才是错的） |

实测（vehicles 页，把相机临时搬到正上方、藏掉一辆车的影子再画一帧，差异像素就是那片影子）：

| 量 | 读数 |
| --- | --- |
| 轿车影子重心 | 沿影子方向 **+3.62m**（正 = 背光侧）、垂直方向 **1.26m**、**背光侧像素占 100%**（同一机位 130.3px/m） |
| 面积随车高 | 1.5m 轿车 62px → 3.0m 货车 371~779px → 4.05m 半挂 1236~1433px（同一机位同一次取样；转台停在哪一帧会影响可见面积，量级差才是要看的东西） |
| 影长系数 | `cot = 0.625`（每辆都核，容差 ±0.02） |
| 平面长边 | `along = proj + sweep` 加半影后与 `scale.y` 一致（毫米级） |
| 与接地暗部 | 两层报出的影子方向逐个对得上（容差 ±0.005） |

面积不能和上一版（旋转矩形）直接比：矩形的**几何**面积更大（多 24%~51%），但旧贴图"只压车底、往外
迅速淡掉"，露在车外那圈本来就很淡。这一轮又换了混合方式（乘法）与影色（由灯光算），像素阈值下的
可见面积随之变了：正上方同机位，轿车 21915px（旋转矩形）→ 43325px（真扫掠 + 手动渐隐）→ 现在 35078px
（真扫掠 + 物理影核）。第三个数字更小，是因为旧贴图那截"渐隐"在半影带里也会被算进可见像素，
而按物理，那截本该是**均匀的影核**——所以"看起来更大"其实是把不该暗的地方也压暗了。
三种写法里，只有当前这版同时满足"形状对（越界 0 格）"和"深浅有依据（影色由灯光算出，独立复算差 0）"。

### 静态构件硬影：灯杆/雨棚/树冠的影子（`replay/prop-shadows.js`）

车辆有了扫掠阴影之后，同一个画面里的**灯杆、雨棚、机柜、门架横梁、树冠**还是没有影子：接地暗部只能给
它们脚下一小团暗（它自己的注释就写着"真正的树影是硬阴影那一层的事"）。9m 高的路灯脚下只有 1.7m 的暗斑，
真实影子该有 **5.6m** 长；树冠挂在 6~8m 高，它的影子根本不是"脚下一团"，而是**树冠自己投出来的椭圆**。

这一层直接按平行光的投影公式烤，不做"往那边拉一拉"：

| 影子 | 怎么算 |
| --- | --- |
| 方盒（机柜/岗亭/横梁） | 占地矩形 ∪ 它沿影子方向平移 `cot × 自身高度` 的那一份，取凸包 |
| 圆柱/圆锥（灯杆、树干） | 圆盘扫 `cot × 自身高度` → 两端各一个半圆的跑道形 |
| 球（树冠） | 平行投影是**椭圆**：沿影子方向半轴 `r/sin(高度角)`、垂直方向 `r`（58° 时拉长 1.18 倍），再按下面的"斑驳"拆成一簇簇 |

**树影不是一块黑斑，是一簇簇叶子投出来的**。一片实心椭圆投在地上，观感是"树下泼了一盆墨"；真树影
是带光斑的。所以树冠（球类）按六角格切成一簇簇小椭圆，铺在**影子坐标系**里、簇与簇留缝：

- 格距按 `2.5 × 簇半径`，簇半径 = 冠幅 × 0.26（覆盖率约 0.47）——**必须**在影子坐标系里铺，
  因为椭圆沿影子方向被拉长 1.18 倍，等距铺会让相邻两簇在长轴方向上叠起来；两条影子一叠，
  乘法混合就把那块压两次（`tint² ≈ 0.03`，一块死黑），所以宁可留缝：缝就是漏光。
- 格子是确定的（不用随机数），每次加载完全一样，自检可以按公式逐簇复算。
- **叶缝要宽过半影才看得见**：冠幅小于 `3 × 半影`（即冠半径 < 0.5m 左右）的球体不拆——那个尺度上
  叶缝会被 6~14cm 的半影糊平，真实影子本来就该是一整块。判据的两个输入（冠幅、半影）都随数据报出去，
  自检按同一份取整值独立复算"该拆还是该整块"。

两个容易翻车的点都按物理掐掉了：

- **离地高度只贡献整体偏移，不贡献影长**。吊在 6.4m 的门架横梁（自身只有 0.4m 厚）影长只有 `0.25m`，
  但整条影子离梁的正投影 **4.0m** 远——这才对得上"横梁在地面上横一道窄影"的观感。
- **按实际铺装裁剪**。index 的路灯/行道树站在 64×96 广场**之外**（广场 x∈[−32,32]，树在 x≈±40），
  不裁的话 5.6m 长的影子会悬在雾里当空飘着——那比没有影子更假。裁剪是**逐环**做的：树冠越界的只是外圈那几簇。
- **"影子够不够大"和"有多少落在铺装上"是两道门**。第一道量**整块投影**（斑驳前、未裁剪）：大树的影子
  斑驳后只剩一半面积，用画出来的面积当这道门会把大树当小灌木丢掉。第二道才量真正画出来的面积。
- **动的东西不烤**。栏杆臂每帧在转（index 叫 `barrierArm`、lanes 叫 `barrierPivot`），烤一条死影子必然
  对不上；按名字排除后 lanes 的实例数从 258 降到 **244**。

画法不用贴图：轮廓本来就在世界坐标 XZ 上，靠**顶点色**从影核乘数渐变到白（乘法混合里白=完全不变），
所以没有"贴图轴向"这一层容易搞反的东西。树冠与实心构件分成**两个** mesh（画法一样，分开是为了自检能
把树影单独藏起来量），合计 +2 draw call、+1% 三角形。半影宽度按太阳视半径与障碍高度算（实测 0.06~0.14m）。

**覆盖率与格距的关系值得记一笔**：格子铺在影子里，一个格子的面积是 `格距²`，所以覆盖率只跟
格距系数有关（`≈ π/系数²`），跟簇半径**无关**——簇大簇少、簇小簇多，稀疏的格子不能靠放大簇来补。
第一版取 2.5（覆盖率 0.50）时树影明显比真实偏淡：`lanes` 上"硬影的变化落在下半部"从 0.389 掉到
0.312 直接报错。改成 2.12（覆盖率 0.70，叶缝 6~13cm 正好和半影同量级）才对上盛夏密树冠的样子。

**簇心必须铺到边界**（`CANOPY_CLUMP_INSET = 0`）。第一版要求"整簇装在冠内"，结果是树冠边缘一圈没有簇：
`lanes` 上 297 个树冠里 **289 个**因为"重叠那一侧一个簇都没有"被整片刷掉，树影凭空消失一大片。
改成簇心铺到边界为止（簇团自然探出半个簇半径，正好把 `CANOPY_SPAN=0.74` 缩掉的那圈补回来）。
这类"数目对不上"的问题现在由一层**分门记账**直接定位：每个被刷掉的候选都记在
`blocked / plan / tiny / clip / dedupe` 五道门、并按几何类型分开，报告里一行就能看出是在哪一门掉的。

顺手抓到的真 bug：树冠那支多算了一次 `lift`（椭圆整体多飘 `cot×base`，重心核对直接把它顶出来）；
`contact-ao.js` 重构时删掉了 `addContactAO` 里的 `matrix` 声明而第 310 行还在用（`node --check` 查不出
这种运行到才炸的引用）；斑驳改造时按"画出来的面积"当第一道门、把确实落在铺装上的树影当小灌木丢掉；
以及"整簇装在冠内"这条把树影整片抹掉——后两个都是"变化要落在下半部"这条行分布核对先报出来的
（它是拿真实渲染的行分布比，不是拿代码里的数自证）。做对照实验的办法很简单：把 `CANOPY_DAPPLE_MIN`
临时调到 `1e9`（等于关掉斑驳、回到上一版的实心椭圆），同一页再跑一次，就能确定某条核对是被斑驳弄挂的
还是本来就差一点——那一次对照里实心版 0.389（过）、斑驳版 0.312（不过），当场定性。

所以另外搭了两个工具：Node 端的几何冒烟台（把模块按仓库结构复制成 `.mjs` 再加一个 canvas 替身，
`addContactAO` 也能跑，`replay/_smoketool.py` + `replay/_smoke/shadow-check.mjs`）与注入探针的语法预检
（`replay/_probecheck.py`，探针自己语法错会表现为"没有收到探针数据"）。几何 bug 基本都被它们先逮住。

## 归并流程

### 1. 选择文件

如果传入 `--at`，脚本只读取时间窗口覆盖到的小时日志文件。

例如锚点为 `2026-05-14 08:10:04`，窗口为 4 分钟，就会选择文件名中包含 `20260514_08` 的日志。这样能避免跨小时或全天扫描造成的污染。

如果没有传入 `--at`，脚本会扫描整个日志目录，并在标准错误输出警告。

### 2. 初始 key

脚本从两个初始 key 开始：

```text
<车牌>
<车牌>_0
```

例如目标车牌是 `<车牌>`，初始 key 就是：

```text
<车牌>
<车牌>_0
```

后续只要日志行包含当前 key 集合中的任意一个 key，就可能被纳入。

### 3. 明文车牌优先过滤

这是脚本里最重要的防污染规则。

如果一行日志中出现了明文车牌，并且这些车牌全都不是目标车牌，脚本会直接排除这一行。

实现上会先把车牌颜色后缀去掉再比较，例如：

```text
<车牌>
<车牌>_0
<车牌>_1
```

都会被视为同一辆基础车牌 `<车牌>`。

这个规则可以挡住同一车道、同一服务、同一时间窗口内的其他车辆日志。例如日志中明确是 `<其他车牌A>_4`、`<其他车牌B>_0`，而目标车不是它们，就不会因为共用 topic、trace 或时间窗口被合入。

有一种例外需要人工解读：同一条交易报文里可能同时出现目标车牌和另一个识别字段，例如入口牌、出口牌不一致。这种行不会被过滤，因为它仍然包含目标车牌，脚本会保留原文，交给后续分析判断是否属于同一笔交易。

### 4. 提取关联 key

脚本会从匹配到的日志行里提取关联键，用于下一轮扩大匹配范围。

支持的 key 类型包括：

- 明文车牌：`vehicleId`、`feeVehicleId`、`identifyVehicleId`、`plateNum`、`vlp`
- 介质/卡/OBU：`mediaNo`、`cardId`、`cpuId`、`obuId`、`serialNumber`
- 交易链路：`passId`、`tradeId`、`vehiclesignid`
- Redis 流水 key：`WASTE_...`、`BAK_WASTE_...`
- 部分请求文件名：`*_REQ_*.json`、`*_RES_*.json`

提取时会过滤一些明显噪声：

- `NONE`
- `null`
- `null_null`
- 全 0 长串
- URL
- `plateNum` / `vlp` 里的十六进制编码值

### 5. 关联扩展

每一轮归并流程是：

1. 用当前 key 集合扫描选中的日志文件。
2. 找到匹配行后记录时间、文件、行号和原文。
3. 从这些匹配行里提取新的可扩展 key。
4. 把新 key 加入集合，进入下一轮。
5. 如果没有新 key，提前结束。

默认扩展两轮。两轮通常足够把车道日志、服务日志、数据服务流水、Redis key 串起来。

为了减少误扩散，`msgId` 和 `filename` 会出现在输出的 `Keys` 中，但不会作为后续扩展 key 使用。它们太容易把同一窗口内的服务请求批量拉进来。

### 6. 去重与排序

脚本用 `(文件路径, 行号)` 去重，因此同一行即使被多个 key 命中，也只输出一次。

最终按以下顺序排序：

```text
日志时间 -> 文件路径 -> 行号
```

这样可以把车道侧和服务侧日志交错排成一条时间线。

### 7. 线圈物理事件补齐

车检器/线圈日志通常不带车牌，单纯靠车牌和交易 key 无法命中。但在理解车道布局后，这类日志反而是判断车辆实际位置的关键证据。

脚本会在已经归并出的日志中提取车道号，再读取同一车道、同一时间窗口内的车辆检测器日志，并按 `有信号/无信号` 或 `true/false` 状态变化切成物理通行片段。随后选择最接近本次车辆事件锚点的片段，把该片段内的线圈日志补进结果。

当前按两种布局理解线圈：

- ETC 专用车道：`车检器1`、`车检器2`、`车检器7`，其中 `车检器7` 是落杆线圈。
- ETC/MTC 混合车道：`车检器6`、`车检器7`，其中 `车检器6` 是存在线圈，`车检器7` 是落杆线圈。

这一步只在已经确认的车道内取最近的物理通行片段，不会因为同一时间窗口里其他车道的线圈变化而合入无关日志。

## 事件列表模式

`--list-events` 用于已知某个车牌时，不做完整合并，只扫描包含目标车牌的日志行，并按时间间隔聚类。

例如：

```bash
python3 merge_vehicle_logs.py <车牌> --log-dir 20260514 --list-events --gap-minutes 10
```

输出类似：

```text
1. <车牌A> | 2026-05-14 08:10:00 ~ 2026-05-14 08:10:31 | lines=... | lanes=3701643301 | sources=data, etc, field
```

这个模式主要用于先找锚点时间，再用 `--at` 做精确合并。

## 使用建议

- 未知车牌时优先用 `--auto --log-dir <目录>` 批量生成；已知车牌时可以用 `--list-events` 找候选通行，再选最接近交易发生时间的 `--at`。
- 窗口不要开太大。入口/出口成功交易一般 3 到 5 分钟够用，复杂恢复链路可以适当加大。
- 如果输出中出现明显其他车辆，优先检查这些行是否同时包含目标车牌。如果不包含，说明过滤规则可能还需要加强；如果同时包含，通常是同一交易中的识别不一致或入出口信息差异。
- 对 CPC 出口、ETC 出口、入口拒绝、称重缺失恢复这类形态，可以分别生成样本文件做对照。

## 本地样本

`merged_*.md`、`*.docx`、`*.png` 都属于本地分析材料，默认被 `.gitignore` 忽略。可以在本地保留不同交易形态的样本，例如 MTC/CPC 入口、ETC 出口成功、ETC 入口、CPC 出口成功、入口拒绝、称重缺失恢复、标签异常拒绝等。
